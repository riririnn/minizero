# どうぶつしょうぎ環境

3×4 盤の将棋（考案：北尾まどか）。ResTNet 論文の 9×9 囲碁に相当する
「アーキテクチャ比較用の小さい環境」として追加した。

## 1. ルール

| 駒 | 記号 | 動き |
|---|---|---|
| ライオン | `L` | 8方向に1マス |
| きりん | `G` | 縦横4方向に1マス |
| ぞう | `E` | 斜め4方向に1マス |
| ひよこ | `C` | 前に1マス |
| にわとり | `H` | 斜め後ろ以外の6方向に1マス |

- 相手のライオンを取るか、**自分のライオンが相手の一段目に入れば勝ち**。
  ただし入った位置が相手の利きにあれば勝ちにならない
- 取った駒は自分の手番で空きマスのどこにでも打てる
- ひよこは相手の一段目に入ると**必ず**にわとりになる。
  にわとりを取っても、手駒はひよこに戻る
- 同一局面（盤面・両者の持ち駒・手番）が3回目に現れたら引き分け
- 反則は無い（打ちひよこ・二ひよこ・ライオンが取られる手も可）。手数の上限も無い

田中哲朗「『どうぶつしょうぎ』の完全解析」（2009）と同じルール。完全解析の
全局面の勝敗・最善手と照らし合わせるので、ルールはそこから変えない。

初期配置（大文字が先手）。点対称になっている。

```
   a b c
 4 g l e     ← 後手の一段目
 3 . c .
 2 . C .
 1 E L G     ← 先手の一段目
```

## 2. 設計の方針：9×9 将棋と同じ作りにする

ネットワークとのやり取り（特徴量・行動ID・value の向き）は、この fork の
9×9 将棋（`shogi`）と5五将棋（`minishogi`）、つまり AlphaZero のチェス・将棋の
作りに合わせる。どうぶつしょうぎを 9×9 将棋の小さい検証の場として使うためと、
動物将棋の既存の実装（中屋敷・金子 GPW 2019、Pgx）がどれも同じ作りだから。

- **盤は手番側から見た向き**。後手番は 180 度回す（マス `s → 11 − s`）
- **value は手番側から見た値**。MCTS は先手視点で木を持つので
  `toFirstPlayerValue()` で戻す（`zero_actor.cpp` の backup）
- **行動IDは手番側の座標**
- **履歴は持たない**（`kDobutsuHistory = 1`）。完全解析の局面には履歴が無いので、
  学習の入力と評価の入力の形をそろえる。定数を 8 にすれば 9×9 将棋と同じ 8 時点になる

2026-09 までは MiniZero 本家の `breakthrough` を写した作り（盤を回さず、手番の面 2 枚、
value は先手視点）だった。駒に前後があるゲームでは、ネットワークが後手番の逆向きの形を
もう一組覚える必要があり、同じ局面でも向きで一致率が 0.02〜0.08 違い、IG の符号が
手番で反転した（`gpw_paper/IG_基準.md`）。

## 3. 設計

### 盤面

`Piece{ PieceType, Player }` の配列12個。`owner_ == kPlayerNone` が空きマス。
`position = row * 3 + col` で、**row 0 が後手の一段目**、row 3 が先手の一段目。
先手（`kPlayer1`）は row の小さい方へ進む。これは内部の絶対座標で、
ネットワークに渡すときだけ手番側に回す（`relativeSquare()`）。

```cpp
enum class PieceType { kGiraffe = 0, kElephant = 1, kChick = 2, kHen = 3, kLion = 4 };
```

方向は北から時計回りの8方向（`kDirectionRow` / `kDirectionCol`）。
駒の動きを判定する `canReach()` の中で後手の行を反転させている。

### 行動空間 132（手番側の座標）

```
打つ手    3種(きりん/ぞう/ひよこ) × 12マス =  36   action_id 0..35    種類 × 12 + 打つ先
盤上の手  12マス × 8方向                  =  96   action_id 36..131  36 + 動かす駒のマス × 8 + 方向
```

後手番はマスを `11 − s`、方向を `(d + 4) % 8` にして同じ式に入れる
（`decodeAction()` / `encodeMove()`）。打つ手が先なのは 9×9 将棋と同じ。
ひよこの成りは到達で自動なので、成りフラグは持たない。

行動の文字列表記は `a1b2`（移動）と `C*b2`（打つ手）で、**絶対座標**
（列 a〜c、行は先手側から 1〜4）。9×9 将棋の USI と同じ扱いで、人が読む表記は回さない。

### 特徴量 19チャンネル（手番側から見た向き）

```
 0- 4  自分の駒 5種（きりん・ぞう・ひよこ・にわとり・ライオン）
 5- 9  相手の駒 5種
10-11  同一局面の回数（1回目・2回目。3回目で終局なので2枚）
12-14  自分の持ち駒 3種（枚数を盤面全体に敷き詰める）
15-17  相手の持ち駒 3種
   18  先手番なら 1
```

1 時点分の 18 枚の並び（駒、回数、持ち駒）は 9×9 将棋の 1 時点分と同じ。9×9 将棋にある手数の平面は
持たない：手数は上限（9×9 は 512 手で引き分け）があるときに意味を持つが、どうぶつしょうぎには
上限が無く、完全解析の局面には手数が無いので、学習（初期局面以外 0 にならない）と評価（常に 0）で
入力が食い違うだけになる。lc0 も同じ理由で手数の平面を廃止している。
`kDobutsuHistory` を増やすと、この 18 枚が時点ごとに並ぶ（`state_history_`）。

非正方形なので `getInputChannelHeight()=4` / `getInputChannelWidth()=3` を上書きする
（前例: `dotsandboxes`）。

### SFEN

`setFromSFEN("gle/1c1/1C1/ELG b - 1")`：段は後手の一段目から、大文字が先手、
持ち駒は文字（枚数を前に付けられる）。GUI で任意の局面を入れるために使う。

### 終局

```cpp
Player winner_;            // ライオンを取った/入った時点で確定させる
bool is_repetition_draw_;  // 同一局面3回目
```

盤面から毎回計算し直すのではなく、**決まった瞬間に記録する**。
トライ勝ちは「入った位置が相手の利きにあるか」を `isAttacked()` で確かめてから確定させる。
千日手は局面文字列（盤面 + 両者の持ち駒 + 手番）の履歴を数える。

## 4. 検証

- 初期局面の合法手が **4手**（既知の値と一致）：ひよこ前進（相手ひよこを取る）／
  ライオン 左前・右前／きりん 前。ぞうは斜め前が自分のひよこで塞がれている
- 作り直し（2026-11）のときの確認は `scripts/dobutsu_env_check.py`：
  回す前の環境と同じ手順で合法手・終局・勝敗が一致すること、後手番の入力が
  先後を入れ替えた局面の先手番の入力と一致すること、value が手番側の値であること

## 5. 既知の制約

- **相対位置バイアスが正方形盤を前提**にしているため、3×4 では
  `block_unit.py` の2行を直さないと実行時エラーになる（`mdfolder/known_bugs.md` の #2）
- `getActionFeatures()` は空（9×9 将棋と同じ。MuZero 用で AlphaZero では使わない）
- `getRotatePosition()` / `getRotateAction()` は恒等。左右反転の対称性は使っていない
  （`actor_use_random_rotation_features=false`）

## 6. ビルド

```bash
scripts/build.sh dobutsu release
```

登録箇所は2つ。

```
minizero/environment/CMakeLists.txt   include に dobutsu を追加
minizero/environment/environment.h    型定義と env_board_size の既定値（3）
```

`scripts/build.sh` の対応ゲーム一覧は CMakeLists から自動生成されるので変更不要。
